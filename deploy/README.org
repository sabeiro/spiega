*  MCP Server (Jetson + Ollama)

Model Context Protocol server that runs on the Jetson and exposes **tools** that talk to Ollama. Emacs (with gptel + MCP) can connect to this server and use these tools when chatting with Ollama (e.g. list models, show model info, or run a quick chat from the server).

## How it works

- **`/mcp/api/chat`** is the agent endpoint (same container, port 8001). The agent injects all tools (current_date, numpy_*, ollama_*) into every request to Ollama and runs the tool-call loop.
- So **any client** (e.g. `test_connection.sh`, gptel) that POSTs to `https://ollama.jetson/mcp/api/chat` gets a model that **is aware of and can call** these tools. No client-side tool loop is required.
- Use a **tool-capable model** (e.g. qwen3, llama3.1). qwen2.5-coder:3b has limited or no tool support; if it doesn't call tools, try another model.
- **`model` in the request body always wins** (Control UI, gptel, curl). Set `OLLAMA_TOOL_MODEL` only as the **default when the client omits `model`** (faster/smaller model on the Jetson). It no longer overrides an explicit client model.

**Response logging (evaluation)**  
Set `options.log_response: true` or `log_response: true` in the POST body. The agent stores one row per request in SQLite: `req_id`, `model`, `effective_model`, `question`, `answer`, `total_ms`, `max_loops`, `created_at`. Use `req_id` to join with the performance logs (stderr) for evaluation.

## Tools

### Ollama
| Tool | Description |
|------|-------------|
| `ollama_list_models` | List available Ollama model names on the Jetson (JSON). |
| `ollama_show_model(name)` | Show details for a model by name (e.g. `qwen2.5-coder:3b`). |
| `ollama_chat(model, message, stream?)` | Send one user message to a model and return the assistant reply. |

### Date / time
| Tool | Description |
|------|-------------|
| `current_date(include_time?, iso_only?)` | Current date (and optionally time) on the server; ISO 8601 or readable. |

### NumPy math
| Tool | Description |
|------|-------------|
| `numpy_array_op(operation, values)` | Aggregation over a list of numbers: `sum`, `mean`, `std`, `min`, `max`, `prod`, `median`. |
| `numpy_binary_op(operation, a, b)` | Binary ops: `add`, `subtract`, `multiply`, `divide`, `power`, `remainder`. |
| `numpy_unary_op(operation, x)` | Unary ops: `sqrt`, `sin`, `cos`, `tan`, `log`, `log10`, `exp`, `abs`, `floor`, `ceil` (angles in radians). |

### Camera (Jetson cam0 / RPi camera)
| Tool | Description |
|------|-------------|

## Run with Docker (recommended)

From the project root (where `docker-compose.yml` is):

```bash
docker compose build mcp
docker compose up -d mcp
```

The container runs **two processes** (so two ports): **MCP protocol server** on 8000 (for Emacs/gptel) and **FastAPI agent** on 8001 (control UI, tool-injecting chat, health, vision). Nginx exposes both under a single path: `https://ollama.jetson/mcp` → protocol, `https://ollama.jetson/mcp/*` → agent.

**Control** — The agent serves a static endpoint tester at **`https://ollama.jetson/mcp/control/`**. Use it to call Ollama (`/api/tags`, `/api/show`, `/api/generate`) and the MCP agent (`/mcp/api/health`, `/mcp/api/chat`, etc.). With the repo mounted at `/app` (see docker-compose), code and frontend changes are picked up by uvicorn `--reload` without rebuilding the image.

### "MCP temporarily unavailable" (no errors in docker logs)

Nginx returns this when it cannot reach the mcp container (connection refused/timeout) or the upstream returns 502/503. Both processes must listen on **0.0.0.0** so nginx (another container) can connect.

1. **From the host** (project root) — check that the agent responds:
   ```bash
   docker compose exec mcp curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8001/api/health
   ```
   Expect `200`. If you see `000` or connection refused, the agent (uvicorn) on 8001 is not up or crashed.

2. **From the nginx container** — check that nginx can reach mcp by hostname:
   ```bash
   docker compose exec nginx curl -s -o /dev/null -w "%{http_code}" http://mcp:8001/api/health
   ```
   Expect `200`. If this fails, the containers are not on the same network or the MCP server on 8000/8001 is bound to 127.0.0.1 only (see below).

3. **Ensure MCP protocol server binds to 0.0.0.0** — `server.py` passes `host`/`port` from `MCP_HTTP_HOST`/`MCP_HTTP_PORT` (default `0.0.0.0:8000`) into `mcp.run()`. If your SDK ignores these, the server may listen only on 127.0.0.1 and nginx will get connection refused.

4. **Reload nginx** after any config change: `docker compose exec nginx nginx -s reload`

5. **Test from nginx → mcp** (after rebuilding the nginx image, it includes `curl`):
   ```bash
   docker compose exec nginx curl -s -o /dev/null -w "%{http_code}\n" http://mcp:8001/api/health
   ```
   Expect `200`. If the nginx image has no `curl` yet, use the MCP container (has Python):
   ```bash
   docker compose exec mcp python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8001/api/health').status)"
   ```
   From the host, same Docker network as the stack:
   ```bash
   docker compose run --rm --network webui-net alpine wget -qO- http://mcp:8001/api/health
   ```

## Emacs (MCP client)

If your MCP client supports **Streamable HTTP** by URL, add the Jetson server to your MCP hub config. In your `emacs` init (or `~/.emacs.d/`), add to `mcp-hub-servers`:

```elisp
("jetson-ollama" . (:url "https://ollama.jetson/mcp"))
```

If you use a **self-signed cert** for `ollama.jetson`, you may need to allow insecure TLS for that host (e.g. in your MCP client or via `gnutls-verify-error` / equivalent).

If your MCP client only supports **stdio** (subprocess), you can run an HTTP→stdio bridge that connects to `https://ollama.jetson/mcp` and speaks MCP over stdin/stdout, then point Emacs at that bridge process.

| `MCP_HTTP_HOST` | `0.0.0.0` | Bind address. |
| `MCP_HTTP_PORT` | `8000` | Port. |
| `CONNECTION_SCAN_ENGINE` | `local` | `local` = built-in heuristic; `http` = forward batch to `MORPHEUS_INFER_URL`. |
| `MORPHEUS_INFER_URL` | *(empty)* | When set with `CONNECTION_SCAN_ENGINE=http`, POST JSON `{"connections":[...]}` here; expect `{"predictions":[{"verdict":"ok"\|"malicious","score":0..1,"reason?":"..."},...]}` (same length as input). Use a small sidecar that wraps your NVIDIA Morpheus / Triton pipeline. |
| `CONNECTION_SCAN_MAX` | `5000` | Max connections per request. |

## Connection scan (Morpheus-style)

The agent can score **connection payloads** (flow-like JSON objects) and return **ok** vs **malicious** counts.

- **`POST /api/connection_scan`** — single JSON response: `total`, `ok`, `malicious`, `engine`, `results[]`.
- **`POST /api/connection_scan/stream`** — **`application/x-ndjson`**: one JSON object per line:
  - `{"type":"start","total":N,"engine":"…","note":"…"}`
  - `{"type":"progress","processed":i,"total":N,"ok":a,"malicious":b}` (cadence from `progress_every`)
  - `{"type":"item","index":i,"verdict":"ok"|"malicious","score":…,"reason":"…","summary":{…}}`
  - `{"type":"done","total":N,"ok":…,"malicious":…,"engine":"…"}`  
  On Morpheus HTTP errors: `{"type":"error","message":"…"}`.

**Body** (both endpoints):

```json
{
  "connections": [
    {"src_ip": "10.0.0.1", "dst_ip": "8.8.8.8", "dst_port": 443, "proto": "tcp"},
    {"dst_port": 4444, "proto": "tcp"}
  ],
  "progress_every": 1
}
```

**NVIDIA Morpheus** is not bundled in this image. Default **`local_heuristic`** uses rules (ports, payload patterns, optional `risk_score`) plus stable jitter so batches look model-like. For a real Morpheus model, run inference in another service and set **`MORPHEUS_INFER_URL`** so this agent can call it.

The Control UI includes a **Connection scan** panel that streams results and updates live counters.
